# Привязка коммутаторов и портов по LLDP

Дата: 30.10.2026. Статус: проект полной топологии; поддержка хостов реализована отдельным первым этапом.

Наблюдение 03.11.2026: пользователь подтвердил, что LLDP на Huawei S5735 (VRP 5.170, V200R019C10SPC500) заработал. Обсуждавшаяся схема: отдельный SNMP read-view с поддеревьями `internet` и `1.0.8802.1.1.2` (LLDP-MIB), отдельный community на этот view, без изменения `ViewDefault` и настроек других систем мониторинга. Точные применённые команды и имена view/community пользователь не сообщил; секреты здесь не сохраняются.

Eltex: в присланном снимке Pult получает Chassis ID и Port ID соседей, но `lldpRemSysName` и адреса управления пустые. Наличие hostname на соседнем коммутаторе само по себе не гарантирует, что он передаёт TLV System Name и что Eltex показывает его через LLDP-MIB. Для конкретной причины нужны модель и версия Eltex и ответ LLDP по одному соседу. В руководстве Eltex MES 4.0.26.3 указано, что optional TLV, включая `sys-name`, по умолчанию не включены: https://eltex.ru/storage/upload_center/files/56/MES_Series_user_manual_4.0.26.3.pdf . Pult показывает сохранённое имя хоста из базы отдельно, только при явной привязке или однозначном совпадении Chassis ID; это не считается именем, полученным по LLDP. Конфигурация коммутаторов не изменялась.

Обновление 31.10.2026: реализован `main/lldp/automatic.ts`. При включённом SNMP и собственном/наследуемом community сбор стартует после сохранения, импорта и запуска приложения, повторяется раз в 5 минут (проверка расписания раз в 10 с). По умолчанию включён, выключается через `Host.lldpAuto`. Два автоматических запроса одновременно; перебираются только сохранённые адреса. Фоновый снимок патчится в актуальной базе, привязки сохраняются для совпавших endpoint; `Host.lldpRevision` защищает его от старого снимка редактора. Это локальная защита LLDP, не общая ревизия Store. Community передаётся в зашифрованном блоке экспорта вместе с паролями доступа; параметры и выключатель передаются с хостом/папкой. Следующий абзац описывает предшествующий ручной этап.

Обновление реализации: в карточку хоста добавлен раздел «LLDP · соседи» с ручным SNMP v2c-запросом, отменой и дедлайном, портами, Chassis ID, адресами и явной привязкой соседа к хосту базы. Снимок хранится в `Host.lldp`, сохраняется кнопкой «Готово» и переносится с экспортом базы. Открытие карточки не запускает LLDP. Реальное оборудование при разработке не опрашивалось; проверки используют поддельный SNMP-транспорт. Описание ниже отражает исходный проект: SSH-адаптеры, глобальная топология, автоматизация карты и контроль ревизий Store остаются будущими этапами.

Под «привязкой LLDP» здесь понимается сопоставление обнаруженных соседей с хостами Pult и создание/проверка соединений «устройство — порт ↔ порт — устройство» на сетевой карте. Включение LLDP и изменение конфигурации коммутаторов — отдельная задача. Модели и версии оборудования пока неизвестны; совместимость необходимо подтвердить на реальных ответах устройств.

## 1. Вывод

Предлагается отдельный сервис обнаружения топологии: сбор → нормализация → сопоставление → предпросмотр → применение выбранных связей. Основной источник — LLDP-MIB через SNMP; SSH CLI — дополнительный транспорт для поддерживаемых платформ, в том числе за jump-host. Начать с ручного запуска на выбранных хостах и одном листе карты.

LLDP сообщает наблюдаемое соседство. Он не является механизмом аутентификации, не доказывает работоспособность передачи пользовательского трафика и не гарантирует полноту физической схемы. Поэтому обнаружение, идентичность устройства, наличие соседа и состояние порта должны храниться раздельно.

## 3. Сбор данных

### SNMP — первый этап

Использовать наследуемые настройки SNMP и community из main process. Опросить только выбранные хосты, не сканировать автоматически адреса, объявленные соседями. Отсутствие ICMP-ответа само по себе не запрещает попытку SNMP.

Читать локальную идентичность, таблицу локальных LLDP-портов, удалённых соседей и объявленных management addresses. При необходимости дополнять IF-MIB для отображения/сопоставления интерфейсов. Базовая ветка LLDP-MIB: `1.0.8802.1.1.2`; конкретную схему и индексы сверить с MIB поддерживаемой платформы при реализации.

Правила декодирования:

- Chassis ID и Port ID хранить вместе с subtype и исходными байтами. MAC, текст и локально назначенное значение — разные виды идентификаторов.
- `lldpRemLocalPortNum` разрешать через локальную таблицу LLDP. Не предполагать универсальное равенство LLDP port number и `ifIndex`.
- Собирать строки remote table по полному индексу `(timeMark, localPortNum, remIndex)`. `timeMark` и `remIndex` не использовать как постоянный ID связи.
- Management addresses могут отсутствовать или быть множественными. Сохранять семейство адреса; IPv6 link-local без контекста интерфейса не использовать для глобальной привязки.
- Различать: успешная полная пустая таблица, отсутствующая/недоступная MIB, частичный обход, таймаут и отмена. Пустой ответ сам по себе не доказывает, что LLDP выключен.
- При изменениях таблицы во время обхода помечать снимок неполным или повторять его ограниченное число раз. Не делать вывод об исчезновении соседа из несогласованного снимка.

SNMP сейчас работает напрямую по UDP. Существующие SSH direct-tcpip и SOCKS5 TCP не дают ему автоматически доступ через jump-host. Если UDP недоступен, интерфейс показывает причину и предлагает отдельный SSH-запуск.

### SSH — следующий этап

Для каждой платформы — адаптер с фиксированными командами чтения и parser fixtures. Cisco имеет `show lldp neighbors detail`; Huawei — семейство `display lldp neighbor`, включая краткий вариант `brief`. Точные команды подробного вывода и управления пагинацией выбирать по модели/ОС, а не единым списком для всех устройств. Официальные примеры приведены в источниках ниже.

MikroTik `/ip neighbor print` содержит результаты нескольких протоколов. При наличии поля `discovered-by` сохранять происхождение; без доказательства LLDP помечать запись как `unknown`, а не как LLDP. Отсутствующие chassis/port ID не выдумывать из имени или адреса.

Исполнитель использует отдельный канал/соединение и не посылает команды в открытый пользовательский терминал. Поддерживает ограничение вывода, дедлайн, отмену, завершение по prompt, ANSI и пагинацию. Сначала проверяется поддержка `exec`; shell нужен для платформ, где `exec` не работает. Команды конфигурации и автоматическое повышение привилегий в этот сценарий не входят.

Сохранить текущую проверку SSH host key, наследование учётных данных и выбор адресов. Переиспользовать общую очередь handshake, дополнительно ограничить число активных сборщиков: очередь открытия сама по себе не ограничивает длительно работающие CLI-сессии. Фоновый сбор не должен блокировать ручное подключение.

Предлагаемые стартовые лимиты, подлежащие проверке на стенде: 4 SNMP-сборщика, 1 SSH-сборщик через jump-host, дедлайн 30 с на SNMP-хост и 60 с на SSH-хост, до 2 МиБ CLI-вывода. При превышении лимита результат неполный, а не пустой. Автоматический SSH-fallback в первой версии отключён: выбор транспорта виден до запуска.

## 4. Модель данных

Нужно разделить наблюдение устройства, решение о привязке и представление связи на листе.

| Сущность | Предлагаемые поля |
| --- | --- |
| `DiscoveryRun` | `id`, `ownerWindowId`, список хостов, транспорт, время начала/конца, статус, результаты по хостам |
| `DeviceIdentity` | `id`, `hostId`, область сети `scopeId`, chassis subtype + bytes, источник, время проверки; несколько идентичностей допустимы для стека |
| `PortIdentity` | `id`, локальная идентичность устройства, port subtype + bytes, отображаемое имя; `ifIndex`/aliases как необязательные атрибуты снимка |
| `NeighborObservation` | `id`, `runId`, `sourceHostId`, локальный порт, удалённые chassis/port ID, имя, адреса, протокол, транспорт, `observedAt`, полнота и диагностические причины |
| `NeighborBinding` | удалённая идентичность + область сети → `hostId`, способ `manual/chassis/address`, дата и доказательства; конфликт делает привязку неактивной |
| `TopologyLink` | `id`, два endpoint, evidence IDs по направлениям, `firstSeenAt`, `lastSeenAt`, статус свежести и подтверждения |
| Дополнение `MapLink` | необязательный `topologyLinkId`, происхождение `manual/lldp`, флаг запрета автоматического изменения |

Endpoint содержит `hostId`, идентичность устройства и `portId`. Неизвестный сосед остаётся наблюдением до привязки. `DeviceIdentity` означает наблюдённую идентичность, а не криптографически удостоверенную личность устройства.

Долговременные привязки/связи хранить в расширении Store `topology`; снимки и ограниченный журнал запусков — в отдельном кэше main process. Отсутствие `topology` в старой базе трактовать как пустое состояние, старые линии — как ручные. Истечение кэша не должно удалять принятую связь: в ней остаются краткие доказательства и отметки времени.

Область сети нужна для повторяющихся приватных IP и неуникальных идентификаторов. На старте — одна область по умолчанию; если база содержит пересекающиеся сети, до автоматического сопоставления требуется явное разделение. Папка интерфейса не считается областью сети автоматически.

## 5. Алгоритм привязки

1. Собрать локальные идентичности всех успешно опрошенных хостов. Создать индекс chassis ID и индекс всех `hostAddresses`, учитывая область сети. Обнаруженные DNS-соответствия, если понадобятся, хранить с временем разрешения; строка hostname не равна объявленному IP сама по себе.
2. Для каждого соседа проверить существующую ручную привязку. Если новые доказательства ей противоречат — показать конфликт, не подменять хост молча.
3. Найти уникальное совпадение `(scopeId, chassisSubtype, chassisBytes)` с локальной идентичностью известного хоста. Дубликат chassis ID у нескольких хостов — конфликт.
4. Если chassis не разрешён, предложить единственного кандидата по точному management IP среди основного и дополнительных адресов. Противоречие chassis/IP блокирует автоматический выбор. Один IP у нескольких хостов, в том числе с разными SSH-портами, требует выбора пользователя.
5. `sysName`, короткое имя/FQDN, описание и частичное совпадение использовать только как подсказки. Одного имени недостаточно для автоматической привязки.
6. Разрешить порт по subtype/ID. Vendor aliases (`GE`/`GigabitEthernet` и подобные) применять только в проверенном адаптере с сохранением оригинала. Не объединять произвольные порты из-за похожих названий.
7. Сформировать кандидата линии; обратное наблюдение с согласованными портами объединить с ним. Не требовать обратного наблюдения для отображения одностороннего результата.

Постоянный ключ разрешённой линии — канонически отсортированная пара endpoint, сериализованная структурно. A:p1—B:p2 и B:p2—A:p1 дают одну линию; A:p3—B:p4 — другую. Не включать в ключ время опроса или индекс строки SNMP.

При неизвестном порте показывать «порт не определён» и предложение без автоматической дедупликации с конкретным портом. Несколько соседей на одном порту сохранять отдельно и отмечать для проверки. LAG и стек не сворачивать в одну физическую линию без дополнительных данных об агрегации/составе.

Для LLDP нет гарантированной глобальной уникальности идентификаторов. Первое применение даже уверенно найденных связей проходит через предпросмотр; пользовательская привязка сохраняется для последующих запусков. Замена устройства с тем же IP и другим chassis ID создаёт конфликт идентичности, а не бесшумное продолжение старой истории.

## 6. Состояния и обновление

Разделить три независимых измерения:

- Привязка: `resolved / unresolved / conflict`.
- Подтверждение: `one-sided / bidirectional`.
- Свежесть: `current / stale / missing`, плюс отдельный статус последнего сбора.

`current` — сосед есть в последнем полном снимке источника. `stale` — давно нет успешного полного наблюдения, например после двух ожидаемых периодов. `missing` — после последнего обнаружения сосед отсутствует в двух последовательных полных успешных снимках того же источника. Это предлагаемые правила приложения, не LLDP TTL. Если транспорт предоставляет оставшееся время жизни записи, сохранять его отдельно; не подставлять вместо него интервал опроса.

У каждой стороны свой статус. Если A больше не видит B, но B видит A, линия остаётся односторонней с предупреждением. Ошибка/отмена/частичный снимок не увеличивает счётчик отсутствия. Отсутствие опроса второй стороны не означает отсутствие соседа.

Пропавшие связи автоматически не удалять. Ручные линии, подписи, изгибы и позиции сохранять. LLDP-состояние не переопределяет `HostStatus.alive`; статус физического порта требует отдельного чтения, например `ifOperStatus`.

## 7. Пользовательский сценарий

На карте: «LLDP → Найти связи». Область — выбранные хосты или хосты текущего листа. У хоста — «LLDP-соседи». Перед запуском видны транспорт и число устройств. Во время сбора — прогресс, результаты по устройствам и отмена.

Предпросмотр:

| Локальный хост/порт | Сосед/порт | Хост в базе | Основание | Действие |
| --- | --- | --- | --- | --- |
| sw-core / GE0/0/1 | sw-access / GE0/0/24 | sw-access | Chassis ID, обе стороны | Добавить |
| sw-core / GE0/0/2 | switch / port 1 | Два кандидата | Неоднозначный IP | Выбрать |
| sw-core / GE0/0/3 | phone / неизвестен | Не найден | Только имя | Пропустить |

Показывать также «уже существует», «неполные данные», «конфликт с ручной линией». Действия: привязать к существующему хосту, игнорировать, создать хост явно (вне минимального MVP). Не переносить автоматически пароль/учётную запись исходного коммутатора новому соседу.

Применяются выбранные строки. Если хост существует, но его нет на листе — предложить добавить узел. Если один хост представлен несколькими узлами — потребовать выбор конкретного узла. Между разными листами линию не строить; для MVP оба endpoint должны присутствовать на целевом листе. Вложенные листы и зоны не раскрывать/перестраивать автоматически.

При точном совпадении с ручной линией предложить прикрепить LLDP-доказательство, сохранив ручное владение и оформление. Если у ручной линии порты не заполнены, не считать её автоматически идентичной найденной физической линии.

В карточке связи: источник, порты, последнее наблюдение каждой стороны, основание привязки, конфликт и команды «Обновить», «Отвязать LLDP», «Удалить с карты». Удаление линии с листа и удаление глобальной привязки — разные операции.

## 8. Контракты и согласованность

Предлагаемый API:

```ts
lldpStart({ hostIds, transport, adapterId? }): Promise<{ runId: string }>
lldpCancel(runId: string): Promise<void>
onLldpEvent(callback): () => void
lldpPlan({ runId, mapId, bindings }): Promise<{ planToken, changes, conflicts }>
lldpApply({ planToken, selectedChangeIds }): Promise<StoreSnapshot>
```

Типы событий: начало хоста, результат/ошибка хоста, прогресс, завершение/отмена. Main проверяет владельца запуска/плана, существование хостов и листа, допустимость адаптера и параметры. Renderer не передаёт произвольные команды или community. Закрытие окна отменяет его запуск; поздние ответы отменённого запуска игнорируются.

`planToken` хранит ревизию базы и точный набор предлагаемых изменений, имеет срок жизни и одноразовое применение. При изменении базы после предпросмотра пересчитать план и показать изменившийся diff. Применять патч к актуальному состоянию в main, одной записью, затем рассылать `onStoreChanged` всем окнам.

Для защиты от последующей перезаписи старым снимком потребуется расширить общий `saveStore`: передавать ожидаемую ревизию и отклонять устаревшие записи во всех окнах. Одного контроля версии внутри `lldpApply` недостаточно. Запись во временный файл уже обеспечивает атомарную замену файла, но не контроль конкурентных изменений.

Импорт/экспорт: расширить валидацию и merge в `src/main/store/transfer.ts`, переносить долговременные identity/binding/link и корректно сопоставлять ID хостов. При конфликте идентичностей импорт не выбирает победителя автоматически. Кэш наблюдений, активные run/plan и диагностический вывод не включать в перенос базы по умолчанию. При удалении хоста очищать или явно инвалидировать связанные привязки; при удалении листа сохранять глобальные наблюдения.

## 9. Декомпозиция реализации

Предлагаемые новые файлы:

```text
src/shared/lldp.ts                  типы наблюдений, результатов и IPC
src/main/lldp/service.ts            запуски, лимиты, отмена, события
src/main/lldp/snmp.ts               типизированный сбор LLDP-MIB
src/main/lldp/normalize.ts          ID, адреса, безопасные port aliases
src/main/lldp/resolve.ts            привязка и конфликты
src/main/lldp/reconcile.ts          линии, направления, свежесть
src/main/lldp/plan.ts               предпросмотр и патч карты
src/main/lldp/cache.ts              ограниченный кэш наблюдений
src/main/lldp/cli/                  отдельные адаптеры второго этапа
src/renderer/src/map/LldpSheet.tsx  запуск и предпросмотр
test/lldp-*.mjs                    fixtures и проверки инвариантов
```

Этап 1: модель, SNMP, ручной запуск, привязка к существующим хостам, предпросмотр и добавление линий одного листа, контроль ревизий Store. Внешние соседи остаются непривязанными.

Этап 2: CLI-исполнитель и подтверждённые fixtures Huawei/Cisco/MikroTik, доступ через jump-host, ручное создание неизвестного хоста.

Этап 3: отдельный фоновый опрос (предварительно раз в 5 минут), история изменений, уведомления о смене соседа, данные портов и агрегации. Автоматическое применение изменений карты не требуется для фонового обнаружения расхождений.

## 10. Проверки и критерии готовности

| Сценарий | Ожидаемый результат |
| --- | --- |
| A видит B, B видит A, порты согласованы | Одна связь, два доказательства |
| Два физических соединения между A и B | Две независимые связи |
| Повторный запуск без изменений | Нет дублей узлов/линий |
| Есть только одно направление | Одностороннее наблюдение, не ошибка |
| Совпадают имена, но различаются chassis | Не объединять по имени |
| Один IP соответствует нескольким хостам | Требуется разрешение конфликта |
| Chassis заменён при неизменном IP | Конфликт, история не склеивается молча |
| LLDP port number не равен ifIndex | Порт разрешается через локальные таблицы |
| Нет management IP или remote port | Сохраняются неполные данные без выдуманных значений |
| SNMP timeout/частичный walk/отмена | Существующие связи не становятся missing |
| Полный пустой снимок два раза | Отметка missing, без автоматического удаления |
| Изменился timeMark/remIndex, endpoint прежние | Сохраняется та же линия |
| LLDP на LAG/стеке, несколько соседей | Нет потери записей или необоснованного объединения |
| Ручная линия и обнаруженная линия совпадают | Явное прикрепление evidence, сохранение оформления |
| Другой лист/два узла одного хоста | Нет произвольного выбора endpoint |
| Изменение базы между plan/apply или двумя окнами | Устаревшая запись отклонена, изменения не потеряны |
| Старый экспорт и повторный импорт | Старые карты работают; новые связи не дублируются |
| Закрытие окна/ошибка parser/превышение лимита | Сокеты и каналы закрыты; запуск завершён корректно |

Для приёмки нужны обезличенные полные выводы CLI или SNMP fixtures минимум с двух соединённых устройств каждой заявленной платформы, с указанием модели и версии ОС. Отдельно проверить отключённый LLDP, ограничения MIB view, недоступный UDP, пагинацию, стек и параллельные линки. После реализации — typecheck/build, целевые тесты и стендовый просмотр результата карты. В этой работе выполнен анализ исходников и проектирование; опрос оборудования и проверки совместимости не выполнялись.

## 11. Источники и границы достоверности

Структура приложения установлена по перечисленным исходным файлам. Архитектура, состояния, лимиты и этапы выше — предлагаемые проектные решения.

- [MikroTik: Neighbor Discovery](https://manual.mikrotik.com/docs/system-information-and-utilities/neighbor-discovery/) — несколько discovery-протоколов и доступные атрибуты соседей.
- [Huawei: проверка отношений соседства LLDP](https://info.support.huawei.com/network/ptmngsys/Web/tsrev_s/ru/content/s/38_edesk_lldp_neighbors_failing/edesk_lldp_neighbors_failing_edesk001.html) — пример `display lldp neighbor brief`.
- [Cisco NX-OS: LLDP show commands](https://www.cisco.com/c/en/us/td/docs/switches/datacenter/nexus9000/sw/7-x/command_references/show_commands/b_N9K_Show_Commands_703i6x/b_N9K_Show_Commands_703i6x_chapter_01100.html) — подробный вывод соседей, идентичности и портов. Это документация конкретной версии, не гарантия для всего Cisco.

До реализации адаптеров уточнить фактические модели/прошивки, доступность SNMP, наличие пересекающихся адресных пространств и требуемый масштаб. Это влияет на покрытие и настройку лимитов, но не меняет разделение наблюдения, привязки и карты.
